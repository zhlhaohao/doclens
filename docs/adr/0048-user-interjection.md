# ADR-0048: 插话 (User Interjection)——生成中途的旁路询问

日期：2026-10-23
状态：已接受（2026-10-23 访谈定稿）

## 背景

LLM 代理可长时间陷入 tool call / tool result 循环（长任务常态）。期间用户只能旁观（看思考过程 trace）或主动停止（杀伤任务）——没有中间态：想问一句「现在进度如何」、想临时下一条指令（如「改用方案B」），都得等回合结束，或者打断任务。

需求：生成进行中，用户可在思考过程框发起**旁路询问**，模型以纯文字汇报作答，答完**循环继续**原任务，回合不结束。

术语定名：**插话 (Interjection)**——与「交互式提问」（agent 问用户）、「对话式提问」（降级形态，回合终止）、「主动停止」（杀伤任务）、「思考流」（被动接收推理文字）严格区分。插话是唯一「用户发起 + 回合不结束」的形态。术语定义见 CONTEXT.md。

## 决策

### 1. 机制：确定性双阶段（否决：仅提示词软约束）

循环顶检查点发现插话后：

1. **注入**：追加 user 消息（`<user-interjection>` 标签包裹的模板文字——「请暂停所有工具调用……只做文字汇报……汇报后立刻恢复原任务」，与 `<background-results>`/`<inbox>` 注入惯例一致），**不补合成 ack**（汇报本身就是模型真实回复；且 assistant 结尾触发 thinking 模式端点 prefill 400，见 DeepSeek 事故）。
2. **suppress_tools 调用**：请求工具表置空（复用既有硬阈值强制终答机制），模型**物理上无法调工具**，产出必然是纯文字汇报。
3. **循环继续**：汇报入历史（user(插话) → assistant(汇报) 自然配对），下一轮带工具表恢复原任务。

否决「仅提示词注入」：模型可能无视指令继续调工具（汇报被吞），也可能把汇报当终答直接 end_turn（回合结束违背目标），还需 end_turn 后强制续跑补丁——补丁比双阶段更绕，且弱模型上三件事（必有汇报/必无工具/必继续）全靠赌。

### 2. 生效时机：循环顶检查点，不打断在飞步骤（否决：立即打断）

提交后进**会话级单槽位**等待；runner 在循环顶（下一次 LLM 调用前，与 bg/inbox 注入同位）消费。当前在飞的工具调用/LLM 流**不打断**——插话是旁路询问，不该有杀伤力；当前步骤跑完自然送达。纯轮询退避（check_background 热轮询）的等待**可被插话提前唤醒**（不干等退避秒数）。

**回合结束竞态**：提交后检查点未到而回合正常结束（end_turn / 硬阈值终答 / 用户停止）→ 槽位残留插话**丢弃 + toast「回合已结束，插话未送达」**，不转成正式消息（旁路询问静默变 message_user 会很意外；要正式问直接在输入框发）。

### 3. 单槽位，不排队（否决：多条约 3 条上限）

提交是异步 HTTP、注入点在检查点——至少需要一个 pending 槽位（机制决定）。但多条排队**无必要**：消费节奏是「第一条被消费 → suppress_tools 汇报几十秒流完 → 下一检查点立即可消费下一条」，多排队只在「单个长工具期间连发多问」有意义，而那场景可把几个问题写进**一条插话**（自由文本）。槽位占用时再提交 → toast 拒绝；消费后槽位清空、按钮恢复。

### 4. 通道：新端点 + 内存槽位（否决：复用 POST /api/chat）

`POST /api/chat/interject`（body: session_id + text）。不能走 `/api/chat`——生成中锁（409 SESSION_BUSY）正是为防两轮交错写库。槽位挂在会话级（与 interrupt registry 同级），**不持久化**：断开续跑期间照常可提交（agent 在跑，检查点会到）；进程重启槽位消失（回合也没了）。

### 5. SSE 协议：双事件 + 汇报一次性推送（否决：逐 token 流）

- `interject_ack`（data `{}`）：检查点消费时发——前端建插话卡（含用户原话），按钮转「已送达」。
- `interject_report`（data `{text}`）：汇报**全文一次性**推送。逐 token 需为旁路短文再造流式渲染状态机（token 事件与正文缓冲逻辑耦合）；汇报几十~几百字、几秒~十几秒返回，卡片「正在汇报…」占位可接受。
- 丢弃通知复用现有 `toast` 事件。
- SSE 事件只服务流式期间；刷新后靠落库条目渲染，不重放。

### 6. 展示：思考过程时间线内的插话卡（否决：独立聊天气泡）

插话卡（用户问题 + 汇报文本）按时间序渲染在 trace 的工具步骤**之间**（`[grep] [插话卡] [read_file]`）。时序真实（插话就是循环中的一个事件）；且避开流式排序难题——占位 assistant 消息在消息流末尾，插话若成独立气泡会出现「气泡插在 trace 中间」的排序混乱，且 message_user 落库会劈裂回放轮次分组（message_user 是轮起点）。

### 7. 入口：trace 标题栏按钮 + 原生 dialog（否决：行内输入条 / 快捷短语 only）

「思考过程 · N 步 · 进行中」标题栏右侧「插话」按钮（折叠态可用——标题栏常驻），点击弹原生 `<dialog>`（仓库惯例 showModal）textarea + 提交/取消。按钮**仅生成中显示**（非流式无循环可插，不显示而非置灰）；恢复态（断开续跑回页、generating 轮询中）**可用**——同一端点同一槽位。

### 8. 落库：tool_calls 合成条目（否决：独立 session item 类型）

```json
{
  "tool_use_id": "interject_<8hex>",
  "name": "user_interject",
  "input": { "question": "现在进度汇报一下" },
  "output": "（汇报全文）",
  "is_error": false
}
```

- 虚拟工具名 `user_interject`（无真实工具对应），前端 chat-tool-trace 识别此名渲染插话卡，不按普通步骤渲染；`traceStepsOf` 不过滤。
- 按序 append 进 `emitter.tool_calls`（送达时入列、汇报回来回填 output）——与真实调用同数组同顺序。
- 插话 user 消息 + 汇报 assistant 消息都是**真实进过 LLM 历史**的（suppress_tools 调用产物），随 `extract_round_raw_messages` 自然落在该轮 raw_messages——回放逐字节一致，**回放层零改动**。
- 已知副作用：trace「复制全文」会出现 `[N] user_interject`——可接受（复制全文本就是调试视角）。

### 9. 交互豁免

- **轮次预算不计**插话轮（它不是任务收敛性信号；计入会加速熔断、惩罚用户插话）；同参签名检测天然不参与（无工具调用）。
- **仅主循环感知**：子代理（task）与 teammate 各有自己的循环，不插话——插话问的是主任务进度，子代理是主任务的一部分。
- **压缩不受影响**：插话问答是普通历史消息，随既有压缩管线自然处理。

## 后果

- planify：runner 循环顶加插话检查点（消费 + suppress_tools 汇报 + continue）；退避等待可被插话唤醒；新增会话级单槽位设施（或由宿主注入）。
- doclens：`/api/chat/interject` 端点；`_chat_emitter` 双事件；chat.py 槽位登记与回合结束丢弃收尾；前端按钮/dialog/插话卡/事件接线。
- 契约面：`user_interject` 条目格式、`interject_ack`/`interject_report` 事件、单槽位语义——跨模块，改动需同步。
- 旧会话零迁移：无插话条目即无渲染分支，天然兼容。
