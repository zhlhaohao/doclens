# ADR-0017: 上传图片视觉判向自动旋转

上传图片（文件管理 / 日记）存在像素级方向错误（无可用 EXIF 可救），导致页面展示歪、视觉转写错。上传落盘后由后台任务调视觉模型判向（0/90/180/270），需要时像素级旋转同格式重编码落盘，并联动索引重建与 toast 通知。2026-09-08 决议。术语定义见 CONTEXT.md（判向自动旋转）。

## Context

两条上传链路此前已做 EXIF 方向校正（日记 `compress_photo` 每张 `ImageOps.exif_transpose`；文件管理 >9MB 才做），但用户仍遇到方向不对的图片——根因是**像素本身就是横/倒的，且没有（或有错误的）EXIF Orientation 标记**（典型来源：微信/QQ 保存的图、截图、部分安卓相机）。EXIF 校正对此无能为力，只能由视觉模型判断「哪边朝上」。

## Decision

### 1. 判向范围 = 仅两条上传入口，手动拷贝不管

仅 `POST /files/upload` 与 `POST /diary/photos` 落盘后触发；格式范围 `.jpg/.jpeg/.png/.webp`（与上传压缩、视觉解读同一集合）。手动拷贝进工作目录的图不判向。

- **否决「全量走 vision_queue」**：队列覆盖全量索引图像，判向是一次性上传场景动作；且上传链路的判向应发生在转写**之前**（避免歪图白转写一次），挂在串行转写队列里时机太晚。

### 2. 判向 = 独立轻量调用，严格解析

独立视觉调用：「需要顺时针旋转多少度才能正面朝上？只回答 0/90/180/270」（max_tokens=32，成本 ≈ 1/400 次转写）。**严格解析**：strip 后精确匹配 `0/90/180/270` 才采纳，其余一律视为无法判断、不动文件——**宁可漏转，不可错转**（把好图转歪比不转更糟）。

- **否决「合并进转写 prompt」**：转写在歪图上做质量先受损，发现要旋转还得重转写，最坏 2 次调用 + prompt 解析复杂化。
- **否决本地判向（Tesseract OSD 等）**：只对文字图有效，风景/人物照无判据。

### 3. 旋转 = PIL 像素级旋转 + 同格式重编码

JPEG q95 / WebP q90 / PNG 无损；先编码到内存成功后再覆盖写盘（编码失败不动原文件）。所有客户端/模型/查看器看到的都是正向像素，无 EXIF 兼容性问题。

- **否决「只写 EXIF Orientation」**：WebP/PNG 支持参差（日记链路全是 WebP 直接出局），且 VisionWorker 读原始字节不看 EXIF，转写仍歪。
- **否决 jpegtran 无损旋转**：需额外依赖（PIL 不支持），且仅 JPEG 受益，两套路径不值。q95 的重编码损失肉眼不可辨。

### 4. 失败策略 = 不重试、静默降级

调用失败（网络/限流/5xx）不重试，记日志放弃，图保持原样——一次性后台任务，临时故障放弃即可，下张图不受影响。解析失败（§2）同样不重试。

### 5. 执行载体 = FastAPI BackgroundTasks，全局串行锁防限流

上传接口落盘后立即返回；判向旋转挂 BackgroundTasks（同步函数自动进 threadpool）。崩溃丢失可接受（代价仅为该图保持歪）。所有视觉 API 调用（转写 / 判向 / caption）经 `vision_client.call_vision` 的**全局串行锁**互斥——共享同一视觉端点，并发会撞 DashScope 等限流。

- **否决持久队列 + 专用 worker**：为低频操作引入整套基础设施（新表/新状态机）过重。

### 6. 索引联动 = 依赖 FileWatcher 自然重建，旋转前清队列残留

旋转落盘 → 文件指纹变化 → watcher 增量重建 → 重新入队转写（正向图）。零额外编排代码。唯一补充：旋转成功后**主动删除 vision_queue 中该图的 pending/processing 残留行**——上传落盘触发的增量索引可能已把歪图入队，不删会让 VisionWorker 在歪图上白转写一次。

- **否决旋转模块主动调 IndexManager 重建**：与 watcher 路径重复，且让上传模块反向依赖索引层。

### 7. 日记 caption 挪到后台、串在判向之后

日记照片的自动 caption 从「上传响应内同步生成」改为后台链：判向 → 旋转 → 正向图生成 caption → `update_fragment` 回写 md 备注。上传立即返回占位备注「照片」。

- **必须串在旋转后**：caption 直接写进日记 md，**不会**被 watcher 联动重做——歪图上生成的 caption 会永久留档。
- 小节已转成品时 `update_fragment` 返回 False，caption 放弃（降级）。
- 用户上传时已填备注 → 跳过 caption，仅判向旋转。

### 8. 开关与用户感知

- 设置页视觉区加「上传图片自动转正」开关（`VISION_AUTO_ROTATE`，默认开）——自动改写用户文件属有感知副作用，给逃生门；未配置视觉 API 时整个链路跳过（行为同现状）。
- 旋转完成 → WatchBroker 广播 `image_rotated` → SSE → 前端 toast「已自动旋转：文件名」；caption 回写完成 → 广播 `diary_updated` → diary 视图刷新当日记录。

## Considered Options

- 全量图像走 vision_queue 判向——否决（§1，时机太晚、范围过宽）。
- 转写 prompt 附带方向输出——否决（§2，歪图转写质量差）。
- 只写 EXIF 不动像素 / jpegtran 无损旋转——否决（§3）。
- 持久队列 + 专用线程——否决（§5，过重）。
- 低置信转人工确认——否决（违背后台自动初衷；严格解析已兜底）。
- 原图备份到 .cortex——本期不做（严格解析 + 仅上传入口，风险可控；后续误判投诉再补）。

## Consequences

- `doclens/image_orienter.py` 新增：判向 prompt / 严格解析 / 旋转重编码 / 组合入口。
- `vision_client.call_vision` 变为全局串行（转写吞吐不变——VisionWorker 本就是串行；判向/caption 偶尔排队）。
- 上传接口响应变快（日记 caption 不再阻塞响应 5-10s）；代价是 caption 晚几秒出现（占位「照片」→ 自动刷新替换）。
- 旋转触发一次额外的重建 + 重转写（API 花费），仅发生在判向非 0 的图上。
- 旋转后图像元数据中的旧解读（XPComment 等）随重编码丢失——正是期望行为（转写需在正向上重做）。
