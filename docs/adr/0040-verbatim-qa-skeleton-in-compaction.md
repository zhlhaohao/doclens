# ADR-0040: 压缩加逐字骨架——Q&A 原文通道进入压缩后上下文

- 状态：已接受（§2 渲染格式与 §2a 工具事实节 2026-10-16 修订/增补）
- 日期：2026-10-10（修订 2026-10-16）
- 关联决议：ADR-0026（压缩即事实——本决议修正其 Decision 2「全量摘要，不保留尾部」的覆盖面）

## 背景

ADR-0026 之后，压缩产物 = 纯摘要消息对：全部历史（含用户问题原文、
AI 回答正文）经 LLM 转写为 6 节结构化摘要。实测痛点：**人名、年代、
原话措辞等细节经摘要转写易损耗**——摘要第 4 节「重要约束」是二手转述，
用户原句的精确措辞（「不要用 emoji」「给我精确值不要估算」）走样后续接
工作会背叛用户意图；摘要第 6 节虽覆盖末尾若干轮，但早期轮次只剩要点。

transcript 实测（8 份压缩样本）支撑改动可行：Q&A 文本（用户问题 +
AI 正文）仅占上下文 10%~48%（均值 ~18%），大头是 tool_result 里的
文档原文——压缩的主要减负来源本就是工具交互，Q&A 骨架全量保留
对压缩率伤害有限。

## 决策

### 1. 压缩产物：摘要对 + 骨架对

`_compacted_messages` 从 2 条扩为最多 4 条：

- 摘要对（不变）：`[Compressed. Transcript: …]+摘要` / 确认——负责
  **叙事通道**（工具交互的来龙去脉、任务状态）；
- 骨架对（新增）：`[Verbatim Q&A skeleton]\n用户问题原文…` / 简短确认
  ——负责**原文通道**（逐字细节保真）。

compacted 条目 payload 仍与 raw_messages 同构（`{"messages": [...]}`），
回放投影（清空前缀再拼接）零改动，「压缩即事实」哲学不变。

### 2. 骨架内容边界与渲染格式（按角色筛选，不按位置）

- **全部问答轮逐字交错**：每条用户纯文本问题（role=user、content
  为 str，剔除 `<system-reminder>` 注入对）开启一轮；轮内**最后一
  条纯 text 的 assistant 消息**为该轮之答（混合块 = 插话不算；轮
  末仍在工具流中途则该轮答为空标记）。2026-10-10 首版只保「问题
  清单 + 末轮回答」，同日用户实测否决升级为全轮交错。
- **渲染格式（2026-10-16 修订，第三版）**：单节 `##` header 与
  前置摘要对分界；每轮 = `【问】`/`【答】` 标签行 + **自适应
  fenced code block**（内容最长反引号行 + 1，最少 4）包逐字原文；
  空答 = 裸 `【答】` 标签行无围栏；块间空行。两版裸文本格式
  （首版 `- ` 清单式、次版 `【问】xxx` 行前缀式）均被用户实测
  否决——**问答原文本身是 markdown**（标题/列表/代码块/伪装的
  `【问】` 前缀行），裸文本下原文与骨架结构混淆：人读无法分界、
  机器解析（二次压缩搬运）会被原文内前缀行切碎。围栏内 md 失活
  + 字节精确逐字（不 strip）；围栏自适应长度防内容含 ``` 时击穿。
  解析器对三种历史落库格式全兼容——旧骨架二次压缩时自动升级为
  新渲染格式。
- **摘要对不进骨架**：旧压缩产物再压缩时，`[Compressed. …]` 摘要
  对按消息形态识别跳过（否则摘要文本被当「用户问题」收进新骨架，
  泄漏 + 膨胀——首版踩坑回归）。
- thinking / tool_use / tool_result 一律走摘要（骨架零工具内容——
  Anthropic API 的 tool_use 配对约束也因此天然满足）。

与 Claude Code 的 messagesToKeep（按位置保尾部消息流，ADR-0026
已否决）区分：骨架按**角色**筛选，保的是分散在全历史的用户原话，
不是尾部窗口。

### 2a. 骨架第二节/第三节：edit 逐字 + 已读清单（2026-10-16 增补）

编码会话中两类工具事实走逐字通道（用户提议，实测痛点：LLM 摘要
转写丢 diff 精度）：

- **edit_file 逐字**：每次调用的 path + old_text → new_text 全文
  （自适应围栏、时间序、含失败调用）。diff 是精确事实且天然有界
  （old_text 受唯一性约束），转写必丢精度——续接编辑全靠它。
- **已读 / 已写文件清单（分组）**：read_file 与 write_file 的**路径**
  分两组清单呈现（`## 已读文件` / `## 已写文件`，2026-10-16b 用户实测
  反馈读写混排难扫读、分开各归各），各自首现去重（offset 分块重读
  同文件只记一次）、时间序、合计 2K token 独立预算（超出各自丢
  最旧，不挤占问答轮 20K）。
- **write_file 全文不逐字**：磁盘即真相——文件在盘上，要内容可再
  read_file；逐字存骨架 = 白复制一份还挤爆预算。write 在骨架只保
  「该文件被新建过」这一行事实（已写文件分组清单）。

### 3. 20K token 兜底：旧截新保（轮原子）

骨架问答节总预算 20K tokens（estimate_tokens 同口径估算）。超限时以**轮**
为原子单位从最旧开始连续丢弃——轮（问+答）不拆散，拆散会出现「有
答无问」的孤儿回答；被截轮加省略标记。edit 逐字节共享 20K 计量
（edit 记录天然有界，不单列预算）；读/写清单合计独立 2K。最坏退化 =
无兜底的旧行为，但那是预算逼的、语义明确，不是默默丢失。

### 4. 多轮压缩：骨架累积

二次压缩时，进入摘要的历史已含骨架对₁（内存消息列表可按
`[Verbatim Q&A skeleton]` 标记识别）——骨架对₂ = 旧骨架解析出的
问答轮 + 两次压缩之间的新问答轮。细节保真度不随压缩次数递减。
摘要对（`[Compressed. …]` 开头）按消息形态跳过，不进新骨架。
识别与搬运都在 planify 内存消息层完成，不碰 DB、不违反
planify/doclens 模块边界。

### 5. 摘要 prompt 措辞同步

摘要 system prompt 明示：用户问题原文已在骨架中逐字保留，摘要
**不重复转述原话**（第 1/4 节引用时给要点即可）——两通道责任分离，
避免摘要与骨架互相重复。

## 明确不做

- **UI 压缩弹窗口径不改**：仍是 pre → post tokens + 节省%，骨架
  token 数天然计入 post（2026-10-10 决议，Q6）。
- **骨架不进展示层**：对话流展示不变（全量历史照常显示），骨架
  只是 LLM 上下文的消息层结构。
- **不做骨架条数字段**：compact API 响应体不加 kept_questions
  （Q6 选 a 否决 (c)）。

## 后果

- 压缩后上下文 = 摘要对（≤10K 输出）+ 骨架对（≤20K）≈ 30K 上限，
  对 200K 窗口占比可忽略；对 128K 窗口亦安全。
- 极端场景（用户粘贴长文提问 × 多次）触发 20K 兜底时，旧行为
  语义（细节递减）作为最坏情况保留。
- 旧 compacted 条目（无骨架对）零迁移：回放投影照常拼接 2 条；
  新一轮压缩自然按新规则生成 4 条。
- 摘要输入预处理（`_render_for_summary`）不改——摘要输入仍是全量
  瘦身转录（含用户问题），摘要只是被 prompt 要求不重复原话。
