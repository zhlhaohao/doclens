# ADR-0044: 自动上下文压缩移至回合末 + 模态进度锁定

- 状态：已接受
- 日期：2026-10-16
- 关联决议：ADR-0026（压缩即事实——本决议只改触发时机与通知形态，产物与落库管道不变）、ADR-0040（逐字骨架——压缩产物组成不变）

## 背景

旧制（ADR-0026/0040 时代实现）：auto compact 在**工具循环内**触发——
估算 tokens > compact_threshold（窗口 ×0.8）即压，压完 toast 通知，
回合继续。两个实测痛点：

1. **任务质量受损**：压缩后模型在「摘要 + 骨架」上继续干活——正在
   进行中的任务丢失工具上下文细节，后半程工作质量下降；且触发点
   在工具循环中间，压缩（LLM 摘要调用，数十秒）打断任务节奏。
2. **用户无感知控制**：仅事后 toast，用户无法得知压缩正在进行、
   也无法确认结果（手动压缩入口反而有完整模态流程）。

## 决策

### 1. 触发时机：回合末、emit_done 之前

终答（或对话式提问、强制终答）流完 → 超阈检查 → 压缩 → emit_done。
回合**全程在完整上下文上执行**；压缩产物（摘要对 + 骨架对，ADR-0040
三节结构）与 `last_compaction` 落库管道零改动。

三个 done 出口统一接入：正常终答 / 对话式提问终止（waiting_user）/
工具轮硬阈值强制终答。**中断出口（stopped）与异常出口不压**——
上下文原样保住供用户重发。

### 2. 循环内不再有任何 auto 压缩（含紧急水位兜底）

明确否决「95% 紧急水位静默压缩」双层制（用户决策）：超长轮撞窗口
硬上限 → LLM 调用报错回合失败，重发时自然先压再跑——语义最简单，
不为极端场景保留中途压缩路径。microcompact（清旧工具结果，无 LLM
调用）维持循环内原位不动。

同日核澄清（用户提议、查证后维持现状）：microcompact 清理的是
tool_result（输出），**从未触碰 tool_use 的 input**——骨架三节的
数据源（edit diff / read 路径）不受影响，read/write/edit 无需豁免。

### 3. 通知协议：notice 通道携带结构化压缩进度

`emit_notice` 协议扩展可选 kwargs：`compact_phase`（"start"|"done"）
+ `pre_tokens`/`post_tokens`。Web 宿主把带 compact_phase 的 notice 转
**专用 SSE `compact` 事件**（不带该字段的普通 notice 仍走 toast，
旧宿主兼容）。

### 4. 前端：不可关闭的模态进度框（复用手动压缩弹窗）

`compact` 事件 → 复用 `compact-confirm-dialog`（ADR-0026 手动入口
同一组件）：start → running 态（模态 spinner，拦截 ESC/backdrop，
锁定页面交互防干扰）；done → done 态（pre→post tokens 结果，「完成」
按钮才可关）。兜底：SSE done 到达而压缩 done 事件丢失时强制撤下
running 模态（防卡死）；手动压缩弹窗在场时 auto 事件让位（同一次
压缩不叠两个模态）。

## 明确不做

- **不改压缩产物**：摘要对 + 骨架对三节（ADR-0040）原样。
- **不改落库管道**：`last_compaction` 打标 → chat.py 轮末落库，
  压缩即事实（ADR-0026）不变。
- **不改阈值**：窗口 ×0.8 与旧制同口径。
- **auto 压缩 done 态不带 compacted_text**（复制按钮不出现）——
  SSE 事件保持轻量；需要审核转录走手动压缩入口。

## 后果

- 回合内上下文不再突变——跨轮 prompt 前缀缓存在回合内绝对稳定
  （microcompact 仍可能在 80% 后清旧工具结果，与旧制一致）。
- 极端场景（单轮工具循环极长、上下文从 80% 冲到硬上限）回合失败
  一次、重发即愈——接受该退化（用户明确选择）。
- 压缩期间用户被模态锁定无法输入——数十秒成本，换来压缩不可被
  干扰（用户明确要求）。
