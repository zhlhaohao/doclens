# 日记功能数据模型：年度 md + 片段态/成品态两态

日记是知识库内容：存于知识库内 `日记/` 目录，一年一个 Markdown 文件（`日记/2026.md`），图片存 `日记/images/<日期>/`，参与全文索引与 Git 同步。日记中每一天的小节有两种状态：**片段态**（当日录入的原始片段，带 `HH:MM` 时间戳，小节头部以 `<!-- diary:raw -->` 注释标记）与**成品态**（次日由 AI 归纳重写后的成稿，此后不可变）。录入永远只写「今天」，不存在对过去日的补录；片段态的文字片段可删可编辑（改正文，保留时间戳与 fid）；照片片段可改备注（caption，保留图片路径）。（2026-08-02：由「可删不可改」放宽为「文字片段正文 + 照片备注均可编辑」。）

总结由 GUI 进程负责：每日 00:05 定点总结前一天（启动时补扫错过的时段），发现过去日的片段态小节即调 AI 总结。总结分两层——图片先经视觉模型逐张描述（复用 Vision API 配置），再把「文字片段 + 备注 + 图片描述」交给对话模型（复用 AI 对话配置）以第一人称叙事体归纳成文。降级策略：**逐图降级 + 整日重试**——单张图视觉失败仅该图退化为用备注，不阻塞整日；对话模型总结失败则整日保留片段态、下轮重试，绝不覆盖原文。

照片上传时统一压缩（最长边 1600px、q80），**不保留原图**——日记是记录而非照片归档，控制 Git 仓库体积（原图路径一年数个 GB 不可接受）。此为不可逆决策。

## Considered Options

- 片段存独立小文件 / SQLite：均被否——前者制造大量索引与同步噪音，后者与「参与同步」矛盾且跨设备丢片段。
- 成品与原始片段并存于年度 md：被否——文件膨胀、内容重复；用户接受总结后原始措辞消失。
- 已总结日允许补录并重新总结：被否——改为「录入仅当天」的更简模型，消除重新总结的全部特例。
- 总结用懒触发（打开预览页才总结）：被否——违背「系统自动」初衷。

## Consequences

- 总结依赖两个外部模型配置：未配置对话模型时日记永远停在片段态（有原文保底，不丢数据）。
- 两台设备同一早晨各自总结同一天 → union 合并可能产生两份当日成品（低概率；缓解：总结前重读最新文件确认仍为片段态）。
- 录入与总结仅 GUI 进程实现，TUI/CLI 不做（与 FileWatcher / Git 同步同为 GUI 专属的模式一致）。
