# 缺陷报告

现象：{问题现象}
环境：{环境}

## 步骤
1. 先自己复现至少一次；复现不了就在报告里写「未能复现」和试过的条件。
2. 把步骤缩到最短：去掉和问题无关的操作。
3. 收集证据：报错原文、日志片段（去掉密钥和个人信息）、截图的说明、出问题的输入数据（用编造的样例）。
4. 判断严重程度：
   - **致命**：数据丢失 / 损坏、安全问题、应用崩溃且无法继续
   - **严重**：主要流程不能用，且没有绕过办法
   - **一般**：功能有错，但有绕过办法
   - **轻微**：文字、样式、体验问题
5. 判断出现频率：必现 / 偶现（N 次里出现 M 次）/ 只出现过一次。
6. 只写事实；对原因的猜测单独放在「备注」里，并标明是猜测。

## 模板

```
**标题**：[模块] 在什么情况下，出现什么问题
**严重程度**：致命 / 严重 / 一般 / 轻微
**出现频率**：必现 / 偶现（M/N）/ 一次
**环境**：系统、版本、浏览器 / 设备、相关配置
**前置条件**：账号状态、数据准备等

**复现步骤**
1. …
2. …

**预期结果**：…
**实际结果**：…

**证据**：报错原文 / 日志 / 截图说明
**影响范围**：哪些用户或功能受影响
**备注**：猜测的原因、相关的问题（标明是猜测）
```

## 使用边界

优先使用已有信息；用户的数量、格式和任务范围优先于本文默认模板。工具权限、主目录/附加只读、Plan 模式与预算以当次实际能力为准；不换工具规避拒绝。这里只给工作方法，不授权写入、命令、付费、发送、提交或发布；未执行/验证的步骤如实标明。
