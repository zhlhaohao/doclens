# 代码审查清单

范围：{审查范围}

## 1. 了解改动
- 读 diff（git diff / git show，运行服从本次实际权限；不新增用户禁止的测试），再读被改函数的调用方和被调用方。
- 用一两句话写出这次改动想做什么；看不出来就先问作者。

## 2. 逐项检查
**正确性**
- 边界：空值、空列表、0、负数、超大值、重复、时区、编码。
- 错误处理：失败路径有没有处理？有没有吞掉错误（空的 catch）？
- 并发：共享状态、竞态、重复提交、事务边界。
- 资源：打开的文件、连接、定时器、监听器有没有释放。

**安全**（涉及输入、权限、密钥、命令执行时再用「安全审查」技能细看）
- 外部输入有没有校验；有没有拼接 SQL / shell / HTML。
- 日志和错误信息里有没有密钥或个人信息。

**可维护性**
- 命名能看懂；函数是否过长、职责是否单一；有没有重复代码。
- 注释解释「为什么」而不是复述代码。

**性能**
- 循环里查数据库或数组（O(n²)）、一次读全表、不必要的重复计算。

**测试**
- 关键路径和修复的 bug 有没有测试覆盖；已有测试是否仍然通过。

## 3. 记录与输出

每条问题先用 `review_finding` 记一条（一次一条，先严重后轻：`path` 相对主工作文件夹，`line` 取改动后源码的行号，整文件问题省略行号；`severity` 取 security / bug / suggestion；`message` 写清缺陷、触发条件和建议改法）。记完再在回复里汇总；只写在回复里的问题，界面和交付证据里看不到。

汇总格式：

```
**改动目的**：…
**结论**：可以合并 / 改完再看 / 需要讨论

**必须改**
1. 文件:行 —— 问题 —— 为什么 —— 建议改法

**建议改**
1. …

**可选**
1. …

**做得好的地方**：一两句
**检查过**：读了哪些文件、跑了哪些检查
```

## 使用边界

优先使用已有信息；用户的数量、格式和任务范围优先于本文默认模板。工具权限、主目录/附加只读、Plan 模式与预算以当次实际能力为准；不换工具规避拒绝。这里只给工作方法，不授权写入、命令、付费、发送、提交或发布；未执行/验证的步骤如实标明。
