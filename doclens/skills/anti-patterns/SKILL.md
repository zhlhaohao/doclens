# 反模式审计与清理（anti-patterns）

对工作目录中的项目做反模式诊断与受令修复。**执行权在用户**：技能默认只审计不动手，产出带优先级的台账报告；用户点名条目下令后才进入执行态。

## 两态协议

| 态 | 触发 | 行为 |
|---|---|---|
| **审计态**（默认） | 用户要求"反模式审计/评审 XX 模块/坏味道清理"（未点名台账条目） | 探索分析 → 写台账 → 给摘要表 → **停，等令** |
| **执行态** | 用户点名既有台账的条目（"修 AP-3""先处理第 2 条"） | 按该条目修复方案执行 → 回归 → 更新台账状态 → 提交 |

边界：用户问"AP-3 是什么问题"属追问不是下令——只解释不执行。普通"讲讲这个项目/这个模块"口头回答，不触发本技能。

## 审计态流程

### 第 1 步：定范围

- **点名范围**（模块轨：用户给路径，如 `src/web`、`api/`；feature 轨：主题词 grep 全仓发现文件，**列清单请用户确认**）——深挖对象。
- **机械扫描恒做全仓**：可 grep 的结构性检查成本近零且问题天然跨模块散布。至少含：跨文件私有成员 import、行数 top 文件（God Object 候选）、同名/同值常量多处定义（Duplicated Source of Truth 候选）、`as any`/裸 fetch 密度。仓库已有架构/风格守卫测试（存在则必跑，如 test_architecture.py、lint 规则集）——它是既有红线，不是本技能产物。
- 仓库自带的纪律文档（CLAUDE.md/AGENTS.md 边界规则、DESIGN.md/design tokens 标尺等，**有则读**）是**附加判据**：违反仓库纪律 = 独立发现，即使形态本身经典。

### 第 2 步：判据——技术栈定制透镜（先检索后使用，分步装载）

判据分两层，载体是**附件**（主体不存清单，SKILL.md 只存流程）：

| 附件 | 内容 | 装载时机 |
|---|---|---|
| `lens/lens-backend.md` | 后端栈主判据（Python 语言层 + Web 框架层 + Pydantic + MySQL/SQLAlchemy + SQLite/FTS5，含两大典型栈组合） | 后端域分析开始时 |
| `lens/lens-frontend.md` | 前端栈主判据（Lit 组件工程 + 原生 H5/vanilla JS + 语义 HTML/可访问性，两形态） | 前端域分析开始时（后端域完成后） |
| `lens/lens-general.md` | 通用形态学兜底词汇表（Wikipedia/Fowler/microservices.io，按域分节） | 随对应域装载该域的节 |

**(a) 栈专属清单的生成与保鲜**：

1. **探测技术栈**（读事实，不问用户）：pyproject/requirements/go.mod 判后端，package.json 判前端。附件 B/C 按**栈小节**组织（后端含 Python 语言层/框架层/Pydantic/MySQL-SQLAlchemy/SQLite-FTS5 五节，前端含 Lit/原生 H5-JS/语义 HTML 三节）——按探测结果装载命中的小节，其余跳过；项目换了附件未覆盖的栈 → 按新栈检索并**重写附件对应节**。
2. **联网检索复检**：每次审计开始时对两附件的栈清单做快速复检（检索词 = `<技术> common anti-patterns/mistakes`；优先官方文档与高星仓库）——清单过时就地更新附件（含来源 URL 与复检日期），再投入使用。
3. **判据声明入台账**：引用附件文件名 + 实际装载的栈小节 + 复检结论。

**(b) 通用透镜使用纪律**：兜底词汇表不是 checklist——每条发现必须绑定项目证据（文件:行号 + 为什么在此架构中构成问题）。

**装载节奏（硬约束——防一次性灌入大量清单导致套模板）**：
- **先后端，再前端**：后端域（含数据库层）分析完成、候选观察收齐后才启动前端域；判据分批装载不混装。
- **每批装载后立即用**：子代理 prompt 只附"本批正在用的判据"（对应附件的相关节），不提前塞全量。

### 第 3 步：探索分析（分域并行执行）

- **顺序：先后端域，再前端域**——后端域（含数据库层）分析完成、候选观察收齐后才启动前端域；两域判据分批装载不混装。**域内并行**：同一域的多组子代理并行清查（收齐该域全部组的笔记才进入下一域）。
- 两遍读法：先 grep 骨架（签名/docstring），仅枢纽文件全文精读；
- **分组派发子代理（双重上限）**：
  - **组内负载**：每组 ≤15 个常规文件（大文件 2 倍计权），**判据 ≤8 条**——组越大配的判据越少，两者乘积是子代理的注意预算；超了就再切组；
  - **并发节奏**：每批 ≤6 个子代理同发，**收齐一批的返回物再派下一批**（防同秒并发触发上游网关 429 限流雪崩）；
  - 某组失败/截断 → 对半缩小该组补跑一次，仍败则主代理直接读该组枢纽文件补齐。
- 交叉核实：接口咬合（前端调用=后端路由；事件发布=订阅）、文档-代码冲突以代码为准并标注；
- 审计对象是**证据链**：每条发现必须有文件:行号 + 一句"为什么在此架构中是问题"——没有证据的直觉不进台账。

**子代理 prompt 模板**（照抄填空；每子代理只拿一小份判据）：

```
为《反模式审计》清查以下文件（只读这些）：

范围（精确清单，只读这些，附行数）：
<该组文件相对路径清单>

本组判据（≤8 条，从 lens/lens-backend.md、lens/lens-frontend.md 摘录与本组文件相关的条目；
每条含形态名 + 一句定义 + 检测线索）：
1. ...
2. ...

第一遍（骨架）：grep 扫签名/docstring/关键调用模式定位嫌疑，禁止全文通读。
第二遍（定点）：仅对嫌疑处读上下文 ±30 行取证。

返回结构化中文笔记（≤1200 词）：
① 候选观察：每条 = 形态名 + `文件:行号` + 一句"为什么构成问题"；
② 灰色项：怀疑但证据不足的（注明缺什么证据）；
③ 反证：像反模式但实为有意设计的（附注释/文档出处）。

禁止：无证据泛评（"耦合度较高"）、给修复方案、罗列与判据无关的细节。
```

**子代理 prompt 纪律**（模板之外的硬约束）：
- 判据**按组裁剪**：从附件摘"与该组文件相关"的条目（如纯 model 文件组不附事件循环判据、纯路由组不附语言层判据），不是整节照搬；
- 一批 6 个子代理可各拿**不同判据**（按组性质分工），不必统一；
- 主代理负责：合并去重（同一文件被多组报告同一形态只留证据最全的一条）、灰色项核实、反证归档 P4。

### 第 4 步：定级 P1-P4

| 级 | 判据 | 处置预期 |
|---|---|---|
| **P1** | 正确性/安全已受损（真实 bug、越权、数据丢失风险、性能陷阱已成事实） | 立即修 |
| **P2** | 健壮性/演进能力显著受损（Blocking the Event Loop 未爆、God Object 阻碍一切改动） | 近期修 |
| **P3** | 纯代码组织（无行为影响的重复/死代码/组织混乱） | 择机修 |
| **P4** | 记录即处置（有意设计但无文档的不对称、收益不明的观察项） | 文档化/关闭 |

### 第 5 步：写台账

落盘**项目根** `antipatterns/<范围 slug>.md`（若项目已有 docs/ 体系可放 `docs/antipatterns/`；与生成型文档目录隔离——台账带执行状态，不可被工具全量重生成覆盖）：

```markdown
# <范围> 反模式审计台账
> 审计日期：YYYY-MM-DD｜点名范围：<...>｜机械扫描：全仓（<扫描项清单>）

## 一、判据声明
（引用附件：lens/lens-backend.md（复检结论/更新内容）、lens/lens-frontend.md（同左）、
lens/lens-general.md（通用兜底）+ 仓库纪律文档（有则列出）作为附加判据）

## 二、发现条目
### AP-1 <标题> [P1] [status: pending]
- **形态**：<归类名>
- **证据**：`文件:行号` + 为什么在此架构中构成问题
- **风险**：<不修会怎样（已损/将损>）
- **修复方案**：<步骤级；涉及契约变更须标注>
- **回归验证**：<按项目既有测试体系指定：同名测试 + 触及层相关套件；前端必含 build>

## 三、新型态
（附件清单外项目特有形态：形态名自拟 + 定义 + 证据；多次实证后晋升入 lens/lens-general.md 对应节——附来源与首次实证的台账路径）

## 四、执行记录
| 日期 | 令 | 条目 | 结果（commit） |
```

status 取值：`pending` / `done(<commit>)` / `discovered-during-fix`（修复中发现的新问题，追加条目）。

对话侧只给**摘要表**（条目/级别/形态/一句话），细节在台账——等令。

## 执行态（下令后）

四条护栏，逐条执行：

1. **单条目单提交**：一次下令只做点名条目（用户明确"1、2 一起做"除外）；完成链 = 修复 → 回归 → 台账状态更新 → 提交（commit message 引用 `AP-n`）。
2. **分层回归纪律**：按项目既有的分层回归约定跑触及层测试（项目无成文约定则：改动文件的同名测试 + 其 import 者的测试 + 架构/风格守卫测试）；前端改动必须构建通过（npm run build / vite build 等）；服务端改动按需重启验证。
3. **新问题不扩散**：修复中发现清单外问题 → 追加为新条目（status: discovered-during-fix）→ 继续原条目；**不顺手修**。
4. **偏离即停**：实际情况与台账方案不符（误判/需改契约/影响面扩大）→ 暂停，向用户呈差异，确认后再动。

## 失败模式（流程约束的成因）

- **套清单式审计**：拿形态名当 checklist 逐项勾选，产出放之四海皆准的空话——每条发现必须绑定项目证据链，无证据不入账。
- **判据脱锚**：不探测技术栈就用通用透镜审——透镜必须针对项目技术栈定制（先检索栈专属清单，通用形态只作兜底）。
- **一次性灌清单**：全量反模式清单塞进单次分析导致套模板——分步装载（先后端再前端）、每批即装即用是硬约束。
- **巨请求/限流**：单子代理整域通读挂死、同秒并发触发上游 429——分组、两遍读法、分批派发是硬约束。
- **审计越权**：审计态改了任何源码文件即违规（台账是唯一产出）；执行态无令先动同样违规。
- **台账失联**：修复后不更新状态 → 台账与实际脱节，编号引用失效——闭环必含状态列更新。
