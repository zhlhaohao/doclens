# 项目架构文档再生成（regen-architecture）

把**当前工作目录中项目**的现状写成给人类读的报告——技术栈不限（Web 前后端、引擎、CLI、桌面、嵌入式均可），一切对象（项目名、模块划分、流程、接口）在运行时从仓库实际结构**发现**，不做任何项目假设。报告是**构建产物**：每次调用全量重生成、整文件覆盖，不增删合并旧文。

## 两种模式（按用户请求分派）

| 模式 | 触发 | 产出 |
|---|---|---|
| **全量** | 要求"生成/更新架构文档、项目全貌"，未点名具体对象 | `docs/ARCHITECTURE.md`（整文件覆盖） |
| **分册** | 点名模块路径或 feature 主题（"分析认证模块""讲讲回退机制"） | `docs/architecture/<名>.md`（该分册整文件覆盖） |

**分册命名双轨**：
- **模块轨**：用户给了路径（如 `src/core/llm`）→ 文件名由路径机械派生（`src-core-llm.md`），范围 = 该路径子树，零歧义；
- **feature 轨**：用户给了主题词（如"认证""回退""视觉解析"）→ 预检 grep 全仓发现涉及文件（跨域散布）→ **列文件清单请用户确认**后再跑；文件名取主题 slug（`auth.md`、`rewind.md`），分册头部记录主题词——每次重生成按主题词**重新发现**文件（feature 的文件集合随代码演进漂移，不重新发现就会悄悄漏）。

## 何时跑

仅当用户明确要求（重新）生成/更新架构文档、或点名分析某模块/feature。普通"讲讲这个项目"类提问不跑本技能——直接口头回答。

## 血泪教训（为什么流程长这样）

1. 单子代理读整域几十个文件会把巨量内容塞进单轮 LLM 请求，请求挂死无响应（2026-10-03 实测：五组直派，70 分钟零进展）。
2. 大量子代理同秒并发会触发上游网关 429 限流，SDK 内建重试耗尽后子代理报废（同日实测：21 组同秒并发）。

因此：**切组必须先预检机械算、读法必须两遍（骨架先行）、派发必须分批（每批 ≤6）、绝不许子代理整域逐文件全文通读**。两种模式一体遵守。

# 全量模式（六步）

### 第 1 步：建提纲

读现有文档（**有则读、无则跳过**，不假设存在）建立叙事提纲：

1. 项目自述文档：`README*` / `CLAUDE.md` / `AGENTS.md`（通常含技术栈与结构说明）；
2. 术语/决策文档（如存在）：`CONTEXT.md`、`docs/adr/` 全部标题、`docs/*.md` 标题清单；
3. 工程定义文件（判断技术栈与模块布局的第一事实源）：`pyproject.toml` / `package.json` / `go.mod` / `Cargo.toml` / workspace 定义等。

**完成标准**：拿到初步分域清单（第 2 步会核实修正）+ 候选横切主题清单（端到端流程/接口面/数据持久化/运行时拓扑等，供第 5 步设计章节）+ 决策文档索引（如有）。

### 第 2 步：预检机械切组（必须，不可跳过）

先用 glob/`wc -l` 做**域发现**，再拿精确文件清单机械切组：

**域发现**（从仓库实际结构推断，不套预设）：
- 按顶层/次级源码目录划分（如 `src/`、`server/`、`web/`、`packages/<name>/`、`apps/<name>/`、各语言包根）；
- 前后端混合仓库按入口拆分（前端源码树 / 服务端源码树 / 共享库 / 工具脚本）；
- 域边界拿不准时以 import/依赖方向为准（`import` 图聚类的粗粒度即可）；
- 域数随仓库而定——小仓库 1~2 域，monorepo 可到 6~8 域。

**机械切组**：
- **每组 ≤30 个常规文件**；>1000 行的文件计 2 个名额；超大文件计 3 个；
- 域内文件多就按子目录切多组；**组总数上限 14**——超了就合并小域压回上限，宁可单组略大也不许超组数（防 429 限流）；
- 每组 prompt 必须附**该组的精确文件相对路径清单**，禁止只给目录名让子代理自己逛；
- 排除：依赖目录（node_modules/venv 等）、构建产物（dist/build/out 等）、`*.test.*` / `__pycache__` / 锁文件 / 缓存。

切完向用户预告：「共 N 组子代理分批执行，预计几分钟，期间无消息是正常的（子代理日志见 debug log），请耐心等待」。

**完成标准**：拿到带行数的分组表；每组文件数折算后 ≤30；组数 ≤14。

### 第 3 步：分批并发读码（两遍读法，防巨请求）

**分批派发（防限流雪崩）**：组**分批**派发，**每批 ≤6 个 task 并发**，收齐一批笔记再派下一批。批间向用户简报进度「第 k/N 批完成」。

每批内子代理 prompt 按此模板（照抄再填空）：

```
为《项目全貌报告》深读以下文件，用两遍读法（严禁逐文件全文通读）：

范围（精确清单，只读这些）：
<该组文件相对路径清单，附行数>

第一遍（骨架）：用 grep 扫每个文件的 class/def/函数签名 + 模块顶部 docstring，
建立模块骨架认知。禁止在第一遍读任何文件全文。

第二遍（枢纽深读）：从清单中挑 ≤15 个枢纽文件（入口、被其他模块高频 import、
数据流必经点），仅对这些文件 read_file 全文或按段读；其余文件停留在骨架层
（签名 + docstring 足以写职责行）。

返回结构化中文笔记（Markdown，总长 ≤2500 词）：
1. 模块清单：每模块一行职责（做什么、依赖谁、被谁用）；
2. 关键函数：仅入口与枢纽（函数名@文件 + 一句话职责 + 在数据流中的位置），
   禁止罗列全部函数；
3. 域内流程：2-4 条主要执行流程（谁触发→经过哪→产出什么）；
4. 对外接口：该组供外部消费的函数/类/事件/端点；
5. 数据与持久化：读写的库表/数据文件（结构、生命周期）；
6. 运行时：常驻线程/子进程（如有）；
7. 文档冲突：源码与仓库现有文档（README/CLAUDE.md/ADR 等）不符之处（两侧各说什么）。

约束：宁准勿全——笔记超预算时砍函数细节，不砍流程与冲突。不要寒暄。
```

**完成标准**：全部组笔记收齐；某组失败/截断时对该组**缩小组（对半）**补跑一次，仍失败则由你（主代理）直接读该组枢纽文件补齐——不放弃任何域。

### 第 4 步：核实与交叉

- **代码为唯一真相**：笔记与现有文档（README/CLAUDE.md/ADR 等，如有）冲突时以代码为准写入报告，并在对应位置标注 `⚠ 与 <文档名> 所述不符：<两侧差异一句话>`。
- 路径引用格式 `文件路径:行号`（行号允许近似）。
- 术语对齐：仓库有术语表（CONTEXT.md 等）则对齐其既定术语，不另造同义词。
- **接口咬合**：沿调用关系核对两侧一致——前端 API 调用 = 后端路由注册；上层 import = 下层实际导出；事件发布方 = 订阅方。咬合不上回头查代码。

**完成标准**：冲突标注落实；接口面交叉核对完成。

### 第 5 步：写报告（章节大纲须经用户确认）

覆盖写入 `docs/ARCHITECTURE.md`。**章节结构由你按项目具体情况设计，没有写死的骨架**——用第 1~4 步获得的信息（技术栈、域划分、流程、接口面）判断这个项目值得讲什么，拟出章节大纲。

**设计原则（以下是启发示例，不是清单约束——一切以「这个项目讲什么对读者最有价值」为准，敢于超出示例增删）**：
- 任何项目通常值得：全局总览（项目定位、技术栈表、架构图）开头；各域分章（职责边界｜模块清单表｜域内流程图｜关键函数表｜冲突标注）；测试与构建发布收尾。已有分册的域在章末加链接索引行。
- 例如：前后端项目往往需要**端到端流程章**（3~5 条核心业务链路，从用户入口到持久化，各配图）；
- 例如：有后端服务往往需要**对外接口面章**（REST API/路由汇总表、GraphQL、事件流/SSE/WebSocket 等实时面，有哪个讲哪个）；**数据与持久化章**（ER 图或存储结构、归属者与生命周期）；
- 例如：有前端时，前端域内往往应讲到**模块组织、路由结构、状态管理、组件体系**；
- 例如：有后台任务/多进程往往需要**运行时拓扑章**（Worker 全景、启动入口差异、启动链路）；有配置体系往往需要**配置面章**；有安全机制往往需要安全面摘要节；
- 例如：CLI 项目讲命令体系、桌面项目讲窗口/进程模型、嵌入式讲外设/中断——以及任何示例没覆盖、但这个项目特有的重要维度（性能管线、协议实现、插件体系、算法核心……发现了就为它立章）。

**把章节大纲（每章一句拟写内容）呈给用户确认或调整**，确认后才动笔；用户否决某章或点名加章时按其意见修改再确认一轮。

**头部模板固定**（构建产物声明，任何项目一致）：

```
# <项目名> 架构（项目全貌）

> ⚠ 构建产物：本文件由 regen-architecture 技能全量重生成，勿手改。
> 生成日期：<YYYY-MM-DD>｜基于代码现状，与现有文档冲突处以代码为准并已标注。
```

**图形优先铁律**：凡能用图表达的绝不用文字——架构 `graph TD`、流程 `sequenceDiagram`/`flowchart`、数据模型 `erDiagram`、状态机 `stateDiagram-v2`。文字只承载图无法表达的语义。模块/函数清单用紧凑表格。**禁则**：连续两节以上纯文字叙述；超过 10 行的连续文字段落必须重组为图+短段落。

**完成标准**：章节大纲经用户确认；成文覆盖大纲全部章节；mermaid 语法正确、每图有图题。

### 第 6 步：收尾核验

- 通读全文：各域全覆盖、核心端到端流程齐全、冲突标注落实、术语对齐（如适用）。
- 报告头部生成日期为当日。
- 向用户汇报：已写入 `docs/ARCHITECTURE.md`、文档-代码冲突清单（如有）、建议跟进事项。

**完成标准**：以上三项做完并向用户交代。

# 分册模式（五步）

对用户点名的模块路径或 feature 主题做局部深析，产出 `docs/architecture/<名>.md`。

### 第 1 步：定范围（双轨分派）

- **模块轨**：验证路径存在 → `glob` 拿子树精确文件清单与行数；文件名 = 路径转 kebab（`/`→`-`，去扩展名）。
- **feature 轨**：以主题词为关键词 grep 全仓（含现有文档/决策记录中的相关条目）发现涉及文件，跨域收集；**把文件清单（分组归域）呈给用户确认或增删**；文件名 = 主题 slug（英文小写短词；无合适英文就用拼音）。分册头部记录主题词原文。
- 排除规则同全量模式。

**完成标准**：得到用户确认的精确文件清单 + 确定的分册文件名。

### 第 2 步：预检切组 + 分批读码

规则与全量模式第 2/3 步**完全相同**（≤30 文件/组、组数 ≤14、每批 ≤6、两遍读法、同一子代理 prompt 模板——把"《项目全貌报告》"换成"《<对象名>深析分册》"）。分册范围通常 1~3 组即够。

相关决策记录/文档（标题含主题词或模块路径的，如有）此步一并深读：直接 read_file 全文，不派子代理。

**完成标准**：笔记收齐 + 相关决策文档已读。

### 第 3 步：自定章节设计（大纲须经用户确认）

**章节结构由你按对象性质决定，没有统一模板**——判断它是什么，就讲什么：

- 前端模块 → 组件树、状态流（store/订阅）、渲染管线、事件处理；
- 服务端框架（FastAPI/Spring/Express/…）→ 路由表、依赖注入/装配、中间件链、实时事件面；
- 数据访问/搜索引擎 → 索引结构、schema、查询管线、写路径；
- 流式对话/消息系统 → 事件流协议、轮次循环、断连/恢复语义；
- 其他性质类推（语言/框架只是例子，按实际对象判断）。

**三条硬底线（任何分册必须满足）**：
1. 开头「范围界定」节：分析对象边界（含哪些文件、不含什么）；feature 轨写明发现依据（主题词 → 命中了什么）；
2. ≥1 张自选类型的 mermaid 图，画该对象**最核心的机制**（类型自选：graph/sequence/flowchart/erDiagram/stateDiagram）；
3. 全局铁律：代码即真相、⚠ 冲突标注、构建产物头部 + 生成日期。

深度自由：值得下钻到函数级/字段级就下钻（分册就是放细节的地方，与全量报告的「关键函数」口径有意不同）。

**把章节大纲（每章一句拟写内容）呈给用户确认或调整**，确认后才进入第 4 步——用户否决某章或点名加章时按其意见修改再确认一轮。

**完成标准**：章节大纲成形、满足三条底线、**且用户已确认**。

### 第 4 步：写分册

覆盖写入 `docs/architecture/<名>.md`：

```
# <对象名> 深析

> ⚠ 构建产物：由 regen-architecture 技能（分册模式）全量重生成，勿手改。
> 生成日期：<YYYY-MM-DD>｜模式：模块轨/feature 轨｜feature 主题词：<原文，模块轨省略>

## 范围界定
（含哪些文件、不含什么；feature 轨写发现依据）

## <自定章节……按对象性质组织，满足三条硬底线>
```

图形优先铁律与全量模式相同；写作风格约束见「约束」节的**人类可读性铁律**。

**完成标准**：分册写入、底线逐条自查通过。

### 第 5 步：收尾核验

- 通读：范围界定准确、图正确、冲突标注落实、术语与仓库术语表对齐（如适用）。
- 向用户汇报：分册路径、发现要点、文档-代码冲突清单（如有）。

**完成标准**：以上做完并向用户交代。

## 约束（两模式共用）

- 子代理只读（Explore），不修改任何文件；全量模式只写 `docs/ARCHITECTURE.md`，分册模式只写该分册文件，互不触碰。
- 两模式独立生成：全量不刷新分册，分册不动主报告（主报告下次全量重生成时自然带上分册链接索引）。
- 报告语言：中文；受众：人类（叙事可读）。
- **零项目假设**：本技能对任意技术栈通用——项目名、域划分、流程、接口、配置命名空间、构建方式全部运行时发现；现有文档（README/CLAUDE.md/CONTEXT.md/ADR 等）是线索而非事实，不存在就跳过、存在但过时以代码为准。

### 人类可读性铁律（写作风格）

受众是不熟悉这段代码的人类读者（新同事/未来的自己），**不是给 AI 消费的压缩语料**。每写完一节自查：「一个没读过源码的人能顺着读完吗？」不能就重写。具体：

1. **完整句子，有主语有动词**——禁止电报体。「压缩管道（循环顶部）：usage-based token 估算一次两用——microcompact 门控（threshold×GATE_RATIO，清旧 tool_result…）」是反例；正例：「每一轮开始前，agent 先检查上下文是否吃紧。检查的依据是上一轮 LLM 返回的 token 用量：轻度吃紧时只清理旧的工具结果（microcompact），严重超限时才把整段历史压缩成摘要（auto_compact）」。
2. **代码标识符按需出现**——函数/常量/字段名是「定位线索」不是内容本身：先用人话讲机制，再括号附名（「清旧工具结果（microcompact，`context/compact.py`）」）。一句话里 ≤2 个裸标识符；连续三个以上代码名的句子必须拆分或改为表格。
3. **机制讲 why 与 what，流程讲 step by step**——每节开头一两句讲这个机制解决什么问题、为什么存在；步骤用完整句逐条叙述，不塞进一行顿号长句。
4. **密集细节用表格或图承接**——参数/阈值/状态枚举这类天然表格物不写成行文；多分支时序画 sequenceDiagram 而不是文字模拟。
5. **中英混排有解释**——领域词首次出现给一句人话（「轮次预算（防止 agent 无限调工具不收尾的保险丝）」）；后续引用可直接用。
6. **数字与符号自解释**——`[:500]`、`×0.8`、`keep=10` 这类字面量出现时必须带单位与含义（「摘要只保留前 500 字」「阈值为上下文窗口的八成」）。

反例特征速查（出现即重写）：冒号开头罗列、破折号串联三段以上、一句超 60 字、标识符密度过半、无解释的缩写。

- 代码为唯一真相；不复述决策文档正文（细节指向其文件）。
- mermaid 消费场景是 GitHub/VSCode/IDE（部分 Markdown 预览器不渲染）——按此预期排版。
